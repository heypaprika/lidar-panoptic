# 엔지니어링 노트 — sparse-3D panoptic을 실제로 돌리기까지

toy 예제에서 **실제 LiDAR 데이터 · batch>1**로 규모를 올릴 때 물리는, 문서에 잘 안 나오는 것들을 정리했습니다.
다음에 이 파이프라인을 세우는 사람(과 미래의 나)을 위한 레퍼런스입니다. 각 항목은 **증상 → 원인 → 수정 → 교훈**
순으로 짧게 적었습니다. 대부분은 특정 라이브러리 버그가 아니라 sparse-3D 전반에 적용되는 함정입니다.

---

## 1. sparse-conv 좌표 열 순서 규약이 조용히 데이터를 오염시킨다
- **증상**: stride-2 다운샘플 conv인데 출력 nnz가 오히려 늘고(94k→130k) 좌표가 음수로 폭주. 에러는 안 나고
  몇 레이어 뒤에서야 CUDA 크래시.
- **원인**: 라이브러리마다 좌표 규약이 다르다. torchsparse v1.4는 `[x,y,z,batch]`(batch 마지막),
  torchsparse 2.x·spconv는 `[batch,x,y,z]`(batch 첫 열). 단일 스캔이면 batch 열이 전부 0이라, 잘못된 규약을
  줘도 **에러 없이** x좌표를 batch로 오독하고 다운샘플이 망가진다.
- **수정**: collate에서 `[batch,x,y,z]`로 통일.
- **교훈**: 좌표 레이아웃은 단일 conv sanity 테스트로 먼저 검증하고, 인코더를 따라 **nnz 추이**를 찍어 본다.
  다운샘플에서 nnz가 늘면 무조건 뭔가 틀린 것이다.

## 2. 실제 LiDAR 좌표는 음수이고 무경계다
- **증상**: 합성 데이터(비음수·작은 범위)에선 되던 게 실데이터에서 깊은 다운샘플 단계에서 깨짐.
- **원인**: KITTI는 센서 뒤·왼쪽·아래의 점이 있어 `floor(xyz/voxel)`이 음수를 만든다. sparse-conv 커널맵은
  대체로 비음수 좌표를 가정한다.
- **수정**: 스캔마다 좌표를 per-axis 최솟값만큼 시프트해 ≥0으로. 기하는 그대로이고, 클러스터링은 float `xyz`를
  쓰므로 영향 없음.
- **교훈**: sparse 라이브러리에 좌표를 넘기기 전, 비음수·유한 범위를 보장하라.

## 3. 좌표 flatten의 int32 한계 — "batch를 키우면 터진다"는 스케일 버그
- **증상**: `batch_size` 2까지는 학습되는데 3부터 `CUDA error: an illegal memory access`.
- **원인**: spconv는 좌표를 `batch·(X·Y·Z) + …`로 **int32 평탄화**한다. 무경계 KITTI 범위는
  ≈3200×3200×120 ≈ 1.2e9이고, 여기에 batch>2를 곱하면 2³¹(2.147e9)을 넘겨 오버플로 → 잘못된 메모리 접근.
- **수정**: 점군을 고정 범위 `[-50,-50,-4, 50,50,2]`m로 crop → 볼륨을 ≈2000×2000×120 ≈ 4.8e8로 결정적으로
  bound. batch 4까지 1.9e9 < 2.147e9로 안전(표준 KITTI 전처리이기도 함).
- **교훈**: 이건 도시 규모 데이터에서 그대로 재현되는 스케일 버그다. **좌표 볼륨을 항상 예산으로** 생각하고,
  더 키우려면 voxel을 키우거나 범위를 좁혀 볼륨을 줄인다.

## 4. sparse-conv 커널은 GPU 아키텍처·버전에 민감하다
- **증상 A**: torchsparse 2.0.0b의 stride-2 conv가 근본적으로 오작동(깨끗한 입력에서도 nnz 2배↑, 음수 좌표).
- **증상 B**: 백엔드를 spconv로 바꾸자 이번엔 첫 conv에서 `Floating point exception`(정수 나눗셈 0).
- **원인**: B는 spconv 기본 implicit-GEMM 커널이 RTX 3090(sm_86)에서 내부 정수 나눗셈 0을 일으키는 케이스.
- **수정**: A는 백엔드 교체(torchsparse→spconv). B는 모든 conv에 `algo=ConvAlgo.Native` 지정으로 문제
  커널 경로 회피.
- **교훈**: sparse-conv는 라이브러리 버전 × GPU arch 조합에 취약하다. **최소 재현 스크립트**(랜덤 점 몇 개 →
  단일 conv)로 라이브러리 문제와 내 코드 문제를 분리하는 게 가장 빠르다.

## 5. Lightning AMP와 라이브러리 자체 fp16 캐스팅이 충돌한다
- **증상**: `precision=16-mixed`에서 conv의 half 캐스팅 지점에서 크래시.
- **원인**: spconv·torchsparse conv는 이미 `@custom_fwd(cast_inputs=half)`로 자체 half 캐스팅을 한다. 그 위에
  Lightning의 autocast가 겹치면서 문제가 됨.
- **수정**: sparse 백본에서는 `precision=32`로 두고(24GB에 충분), 필요 시 라이브러리 자체 amp 경로에 맡긴다.
- **교훈**: sparse 라이브러리는 정밀도를 스스로 관리한다고 보고, 프레임워크 AMP를 이중으로 씌우지 않는다.

## 6. clean clone에서 돌아가는지 반드시 확인한다
- **증상**: 로컬에선 스모크 테스트가 통과하는데, 새로 clone하면 `import src.data`부터 실패.
- **원인**: `.gitignore`의 앵커 없는 `data/` 패턴이 `src/data/`·`configs/data/`까지 무시해서 핵심 코드가 커밋된
  적이 없었다. 파일은 디스크에만 있어 로컬에선 멀쩡해 보였음.
- **수정**: 패턴을 레포 루트에 앵커링(`/data/`, `/dataset/`)하고 누락 파일 커밋.
- **교훈**: 재현성은 "내 머신에서 됨"이 아니라 "깨끗한 상태에서 됨"이다. `git archive HEAD`로 뽑아 돌려보면
  이런 누락을 바로 잡는다.

## 7. 멀티배치 devoxelize는 순서 가정을 검증한다
- **증상 가능성**: 단일 스캔 forward는 되는데 학습(batch>1)에서 인덱싱이 어긋날 위험.
- **원인**: per-point 예측은 `backbone_out[inverse]`로 복원하는데, 이는 백본 출력 voxel 순서가 입력 voxel
  순서와 같다는 가정에 의존한다. U-Net 디코더는 매칭 `indice_key`로 좌표/순서를 복원하지만, 배치 전체에서
  성립하는지는 확인이 필요하다.
- **수정**: `backbone_out.shape[0] == 점 개수`를 단정(assert)하고, 배치 2로 forward+loss+backward를
  단독 검증하는 스크립트(`scripts/debug_step.py`)로 확인.
- **교훈**: 인덱스 매핑은 조용히 틀리면 크래시가 아니라 **성능 저하**로 나타난다. 명시적 단정으로 조기에 잡는다.

## 종합 — 반복되는 두 교훈
이 함정들은 대부분 규모 있는 실제 3D 데이터에서만 드러난다. 좌표 규약·비음수화·좌표 볼륨의 int32 한계·
커널 arch 민감성은 데이터가 커질수록 함께 커지는 문제다. 결론은 두 가지로 수렴한다 — **(1) 좌표를 예산으로
다룬다(범위·볼륨·정밀도), (2) 최소 재현과 clean-clone 검증으로 문제를 조기에 격리한다.**
